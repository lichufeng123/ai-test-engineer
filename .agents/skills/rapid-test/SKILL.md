# 快速测试模式

快速模式是标准测试流程的前置文档压缩路径，不是自由点击、跳过上下文或降低验证质量。它只暂缓正式需求说明书、正式 BF/A 业务规则生成与审核、正式用例生成与审核；测试工程师思维、业务知识加载、风险控制、Oracle、证据和问题定性仍然必需。

## 多端权限覆盖（必需）

涉及权限的设计、测试和修复回归，先读取 [权限测试设计规范](../test-case-generate/references/permission-testing.md) 的“多端 × 权限组合”要求。先盘点全部适用配置端与消费端，再逐端列权限组合并绑定用例；执行后逐格登记 run_id、状态和证据。一个端通过不能代表其他端通过，商家版不能因同属 H5/Web 被省略。阻塞/未执行/有依据不适用必须明确，快速与一站式模式同样执行。

## 交互体验覆盖（必需）

涉及 UI 的用例设计、执行及回归，必须读取 [交互体验检查](../requirement-grounded-functional-testing/references/interaction-experience.md)，在既有计划/章程中逐项评估六个维度，执行时留存过程证据，并在报告回填覆盖与问题分流。快速、一站式模式也不得省略；最终数据正确不能代替交互体验通过。

## 适用方式与效力

当用户要求“快速测试 / vibe coding / 先测再补文档”，或标准产物尚未完成但需要尽快发现问题时，向用户说明该模式结果为临时结论。用户明确指定快速模式即已确认进入模式；已有标准工作项按同一需求增量更新为 rapid，不重建竞争需求，也不要求用户重复确认。正式 `CASE_DESIGN` 门禁、规则审核回执、Current 同步和正式用例基线不是 rapid 探针的执行前置。不可把快速结果冒充已审核基线的完整通过、验收或发布门禁。

先确认本次目标、环境、平台、时间盒、范围内/外事项、账号角色的运行时可用性、写入授权和禁止动作；本轮用户明确授权必要的隔离 SIT 造数和命名测试动作时，可在逐探针身份/Oracle/清理边界就绪后自主执行，不得因缺正式规则/用例回执或再次索要例行许可而停整轮。生产、批量、真实通知及未获授权的不可逆资金/客户影响仍按独立授权边界处理；某探针没有可判定预期或独立 Oracle 时只阻塞该探针，其余已就绪探针继续。Mock 必须明确与真实系统隔离，说明覆盖边界，不把 Mock 结果说成真实端到端通过。

## 不能跳过的上下文和思考

按项目 `AGENTS.md` 与 `docs/TEST_CONTEXT_INDEX.md` 加载当前任务、系统知识、已审核业务预期、遗漏风险规则和既有执行资产。快速模式不得跳过遗漏风险库；私有业务仓库必须先运行知识注册中心 `validate`、按 feature/stage `load`，并实际读取全部 `required_reads`，尤其检查 `knowledge/test-risks/omission-risk-rules.json`。识别角色/数据范围、业务对象、状态、上下游、异步、缓存/索引、历史兼容、清理和环境。已确认事实、推断、历史信息、待确认问题分开记录。

开始任何业务动作前，必须形成并保存本任务的轻量测试计划/章程，作为快速模式的执行计划。至少包含：目标与成功条件、风险假设与优先级、知识与正式预期来源（缺失项明确写无）、目标平台/环境/版本、范围/排除、覆盖探针、角色、Fixture 来源和唯一性、断言及独立 Oracle、证据、业务写入预算和授权、停止/清理条件及结论效力。可使用 `templates/rapid-test-charter.example.json`，按 `schemas/rapid-test-charter.schema.json` 填写；计划按单次 run 绑定并在动作前冻结。

快速模式不会替你生成或批准正式测试用例，也不会创建正式基线。它可以生成临时风险清单和可执行探针/断言计划用于本轮探索；必须标注 provisional，不能伪装成正式 Case ID、用例库记录或基线。若要生成正式用例，需切换标准流程并通过规则/用例评审门禁。随后按风险驱动探索循环工作，而非一次性猜完所有用例。

## 探索同时为自动化消除未知项

首轮探索前逐项列出“要消除的未知”：稳定入口/业务键、角色和Fixture、独立Oracle、页面/接口状态和等待条件、可安全重试/停止点、持续录屏与错误截图触发点；每项指定预期可执行资产或具体阻塞回执。一个未知已回答，不得下一轮重新做同一自由探索；转为现有正式自动化包内的代码和单元/安全环境验证。记录见解的JSON、截图或聊天摘要不等于可执行资产。探索失败时保存问题、证据、负责人及期限，不用新的rapid运行假装回归。

首次探索收尾及同功能任何重复执行前，准备 `schemas/exploration-handoff.schema.json` 对应的工作项回执，运行 `ai-test exploration-handoff-check --input <run.json> --root <project> --output <receipt.json>`。首次探索缺可执行资产只能称“资产交接未完成”；重复执行即使仍标rapid，也不能以Ego再次自由点击代替回归。门禁阻塞时可继续经计划限定的只读诊断或获单独授权的应急恢复，但不得把它们计为自动化回归或重复不明状态的业务提交。需要正式放行仍必须完成唯一审核基线和标准门禁；该检查不能替代业务授权。

## 动作前探针冻结

每次关键操作前为本轮探针冻结并记录：

1. 探针 ID、风险假设和测试意图；
2. 前置状态、角色、目标业务实体及唯一定位条件；
3. 原子断言及预期值/状态；
4. Fixture 来源、唯一键、时间/组织范围、当前状态；
5. 独立 Oracle 和证据来源；
6. 本次具体动作、是否写入、授权/副作用边界；
7. 超时、停止、清理/恢复条件。

Fixture 与被验证的预期必须解耦。不要用待验证评分/状态定位目标，不依赖“最新一条”，不以被测两端相等作为存在性证明。出现零命中、多命中、身份不一致、Fixture 不确定、Oracle 不独立或关键预期未确认时，停止该探针并记为阻塞/待确认。

动作后记录原始观察与证据，再决定下一探针。新发现可改变后续探索方向，但不得倒改已经执行探针的断言或判定；须写明新证据、原因、影响并创建新探针版本。AI/代理可建议探索动作，不得替用户选择业务目标记录、修改业务预期或作正式裁决。

## 结果分类与升级

逐条报告通过、失败、阻塞、未执行。快速测试只有在该探针的所有断言、Fixture 身份和独立 Oracle 都被实际证据覆盖时，才可标“临时通过”；脚本绿灯、页面可见、HTTP 成功、两端共同漏数均不足以通过。异常先区分产品、环境、Fixture、权限、异步、缓存和脚本因素。

运行结束输出：已验证范围、未覆盖/阻塞项、失败证据、临时结论效力、业务写入/清理结果、上下文冲突和建议动作。发现缺陷、关键业务规则缺口、跨端/权限/数据完整性风险，或需要用于发布/验收/重复回归时，升级标准流程并补需求、审核规则和正式用例；不得因快速运行成功关闭这些任务。纯一次性探索可暂缓正式产物，但须记录未完成项、负责人/责任方和后续处置期限。新的业务知识或测试风险先进入待审核区，不自动晋升。

## 必须遵循的记录链

若进行了自动化执行，首个测试动作前按框架执行日志流程登记，结束时保留成功、失败、阻塞或中断状态。每个 run 保存轻量章程、探针计划/版本、执行回执、证据清单、问题定性和收口记录；不得将它登记成新的正式用例基线。
## 可选缺陷提单

测试开始时按项目配置查询并确认本轮版本；完成问题定性后，已获提单授权且适配器前置就绪时使用 `ai-test defect-submit --execute`，遵循 [统一提单流程](../requirement-grounded-functional-testing/references/defect-submission.md)。只回填已验证的Bug引用；缺配置、凭据、版本或适配器模式前置时只阻塞提单，不阻塞其余已授权测试，不为快速探针伪造正式Case。
