# 快速测试模式

快速模式是标准测试流程的前置文档压缩路径，不是自由点击、跳过上下文或降低验证质量。它只暂缓正式需求说明书、正式 BF/A 业务规则生成与审核、正式用例生成与审核；测试工程师思维、业务知识加载、风险控制、Oracle、证据和问题定性仍然必需。

## 适用方式与效力

当用户要求“快速测试 / vibe coding / 先测再补文档”，或明确指定在 SIT 先测试某功能而正式需求/规则/用例尚未就绪时，按已给目标与环境进入快速模式并说明结论为临时结论，无需再次请用户确认“是否进入快速模式”。若用户明确要求“一站式测试/一步到位生成用例并执行出报告”，转用 `one-pass-test`，先展示临时 `OP-*` 用例再在同一轮执行和报告；两种模式的临时结果都不可冒充已审核基线的完整通过、验收或发布门禁。

先恢复功能地图与既有运行，再确定本轮目标、环境、平台、范围、角色、Fixture、允许动作及禁止动作。接手时先从经审核账号/Fixture 索引按 SIT 环境、角色、组织范围唯一选定非敏感账号别名和登录方式，记录在现有章程的可选 `account_selection` 字段，不另建审批表；多个候选或缺账号时在打开登录页前一次性询问，不能临登录才问“用哪个账号”。同一任务优先复用并核验已有登录态；没有登录态且有合规运行时凭据时按既有受控入口登录；需要人工登录时仅在浏览器 handoff 实际成功后请用户操作，返回控制后核对真实角色与组织。任务范围已授权不需为每次登录重复请示，账号别名不代表密码可用。用户指定 SIT 导入导出测试，已包含隔离测试 Fixture 的常规创建、UI 文件导入提交、回读和 UI 导出，不必逐次询问或自行缩成只读。生产、真实结算/资金、真实通知、跨范围不可逆操作另行处理；提交终态不明先核实，不盲重传。Mock 必须明确与真实系统隔离，说明覆盖边界，不把 Mock 结果说成真实端到端通过。

## 不能跳过的上下文和思考

按项目 `AGENTS.md` 与 `docs/TEST_CONTEXT_INDEX.md` 加载当前任务；优先查功能地图、工作项索引和历史测试/缺陷，快速恢复已有流程、上次结果及未测范围，再按功能、环境和角色加载适用系统知识、已审核业务预期、遗漏风险规则和既有执行资产。私有业务仓库有注册中心时运行 `validate`、按 feature/stage `load`，实际读取全部 `required_reads`，尤其检查适用的遗漏风险规则。已确认事实、推断、历史信息、待确认问题分开记录，历史通过不继承为本轮通过。

开始任何业务动作前，必须形成并保存本任务的轻量测试计划/章程，作为快速模式的执行计划。至少包含：目标与成功条件、风险假设与优先级、知识与正式预期来源（缺失项明确写无）、目标平台/环境/版本、范围/排除、覆盖探针、角色、Fixture 来源和唯一性、断言及独立 Oracle、证据、业务写入预算和授权、停止/清理条件及结论效力。可使用 `templates/rapid-test-charter.example.json`，按 `schemas/rapid-test-charter.schema.json` 填写；计划按单次 run 绑定并在动作前冻结。

快速模式不会替你生成或批准正式测试用例，也不会创建正式基线。它可以生成临时风险清单和可执行探针/断言计划用于本轮探索；必须标注 provisional，不能伪装成正式 Case ID、用例库记录或基线。若要生成正式用例，需切换标准流程并通过规则/用例评审门禁。随后按风险驱动探索循环工作，而非一次性猜完所有用例。

## 探索同时为自动化消除未知项

首轮探索前逐项列出“要消除的未知”：稳定入口/业务键、角色和Fixture、独立Oracle、页面/接口状态和等待条件、可安全重试/停止点、持续录屏与错误截图触发点；每项指定预期可执行资产或具体阻塞回执。一个未知已回答，不得下一轮重新做同一自由探索；转为现有正式自动化包内的代码和单元/安全环境验证。记录见解的JSON、截图或聊天摘要不等于可执行资产。探索失败时保存问题、证据、负责人及期限，不用新的rapid运行假装回归。

首次探索收尾或准备宣称重复自动化回归时，使用 `ai-test exploration-handoff-check` 检查 runner、Oracle、测试收据、备份及证据计划。缺正式包的临时 SIT 探针仍可在自身计划和证据范围内执行，但只能称探索/临时测试，不冒充已验证自动化回归；未知任务终态不重传业务文件。

## 动作前探针冻结

每次关键操作前为本轮探针冻结并记录：

1. 探针 ID、风险假设和测试意图；
2. 前置状态、角色、目标业务实体及唯一定位条件；
3. 原子断言及预期值/状态；
4. Fixture 来源、唯一键、时间/组织范围、当前状态；
5. 独立 Oracle 和证据来源；
6. 本次具体动作、是否写入、授权/副作用边界；
7. 超时、停止、清理/恢复条件。

Fixture 与被验证的预期必须解耦。不要用待验证评分/状态定位目标，不依赖“最新一条”，不以被测两端相等作为存在性证明。出现零命中、多命中、身份不一致、Fixture 不确定、Oracle 不独立或关键预期未确认时，停止该探针并记为阻塞/待确认。

动作后记录原始观察与证据，再决定下一探针。新发现可改变后续探索方向，但不得倒改已经执行探针的断言或判定；须写明新证据、原因、影响并创建新探针版本。AI/代理可建议探索动作，不得替用户选择业务目标记录、修改业务预期或作正式裁决。

## 结果分类与升级

逐条报告通过、失败、阻塞、未执行。快速测试只有在该探针的所有断言、Fixture 身份和独立 Oracle 都被实际证据覆盖时，才可标“临时通过”；脚本绿灯、页面可见、HTTP 成功、两端共同漏数均不足以通过。异常先区分产品、环境、Fixture、权限、异步、缓存和脚本因素。

运行结束输出：已验证范围、未覆盖/阻塞项、失败证据、临时结论效力、业务写入/清理结果、上下文冲突和建议动作。发现缺陷、关键业务规则缺口、跨端/权限/数据完整性风险，或需要用于发布/验收/重复回归时，升级标准流程并补需求、审核规则和正式用例；不得因快速运行成功关闭这些任务。纯一次性探索可暂缓正式产物，但须记录未完成项、负责人/责任方和后续处置期限。新的业务知识或测试风险先进入待审核区，不自动晋升。

## 必须遵循的记录链

若进行了自动化执行，首个测试动作前按框架执行日志流程登记，结束时保留成功、失败、阻塞或中断状态。每个 run 保存轻量章程、探针计划/版本、执行回执、证据清单、问题定性和收口记录；不得将它登记成新的正式用例基线。
