# 交互体验检查：测试设计、执行与提报

用户于 2026-10-24 确认：测试不仅检查最终功能和数据，也要主动发现、留证并向用户提报不合理、增加操作负担或造成困惑的交互。此确认授权的是测试覆盖要求；具体产品预期仍须有依据。

## 每轮必须执行

1. 页面、App、H5、小程序的标准测试、快速测试、一站式测试及相关缺陷回归，执行前都在既有计划/章程中增加“交互体验覆盖”。用例设计也须评估下面六个维度，不另建竞争基线；纯接口任务注明不适用及原因。
2. 每项写明触发操作、观察状态、预期依据和证据计划。先对照当前 Demo HTML、原型、已审核需求及用户明确说明，区分实际现场与预期参考。未知产品口径不得猜测；继续执行其余有依据的检查。
3. 观察完整过程：操作前、处理中、成功/失败、重试/返回。动态问题保留连续录屏或 GIF 及关键时点截图；最终截图、接口成功或数据正确不能证明过程体验通过。记录环境、版本、角色、目标、操作顺序、用户可见影响及证据。未实测不得写成已复现。
4. 报告逐维度写“已检查（通过/失败/待确认）／不适用及原因／阻塞／未执行”，关联场景和证据。尚有适用维度未执行时，不得宣称交互体验全部通过。只调整已有计划和报告即可，无须创造新的状态机或声称已有 CLI 硬门禁。

## 六个必评维度

| 维度 | 要观察的问题 |
| --- | --- |
| 加载与状态一致性 | 同一查询范围的指标、图表、列表是否混合新旧数据；局部先展示是否误导；加载范围、完成反馈、空态/失败态是否清晰；是否闪烁或重复 loading。 |
| 布局与滚动稳定性 | 内容加载、增删、展开后是否跳动、遮挡、溢出；列表滚动与分页位置是否合理保留；点击“调整/编辑”后编辑区是否可发现、是否需要无提示地手动寻找。 |
| 控件与操作反馈 | 按钮隐藏/置灰/可点击是否符合当前状态；提交、保存、删除是否有明确反馈；是否重复点击、无反馈等待或误触。 |
| 连续操作与输入保留 | 筛选、返回、取消、切换及再次打开是否丢失输入或上下文；键盘焦点和操作顺序是否造成额外负担。 |
| 异常恢复 | 超时、失败、空数据、部分成功、重复提交后是否清楚说明现状并可恢复；重试不得造成重复写入或假成功。 |
| 可读与可达 | 关键文案、状态、分数、禁用态能否辨认；内容过长、常用窗口/设备下是否不可见或无法操作。 |

## 缺陷与待确认建议分流

- 有明确 Demo/原型/需求/用户说明且实际违背，或能复现具体的误导、阻断、输入丢失、无反馈、额外寻找等影响：主动登记并按项目既有提单授权、版本选择、责任人与通知流程提报，不等用户逐个指出。事实、预期来源、影响和推断分开写，先排除环境、缓存、权限、异步和脚本因素。
- 可复现的具体影响本身可构成体验问题依据，不因缺少书面需求而忽略；这不等于批准新的全局产品规则。
- 影响明确但产品口径有冲突，或只有个人配色/审美偏好：向用户呈报带证据的候选问题/建议，说明待确认点；不得包装成已确认产品缺陷，也不得静默丢弃。
- 独立模块允许独立加载，只要状态、数据范围与交互清晰，不误导、不造成操作障碍；不因出现多个 spinner 就自动提 Bug，不设没有来源的毫秒阈值。
- Bug 13307 的用户材料展示了数据概览统一加载与分段加载的差异，适合作为“最终数据正确但过程体验仍需检查”的案例。该页面的统一 loading 要求不能直接推广到所有页面；录屏不证明当前部署已验收，也不证明接口根因。
- 预期参考图标为“预期效果（Demo/原型）”，真实运行图标为“实际现场”；不能把修复后、Demo 或原型图写成修复前现场。
