# SIT 试点流程减负审查（路由文案与可选建议器已调整，业务执行门禁未改）

范围：通用框架 0.13.0a2 开发工作树的流程/代码静态审查。未登录业务系统，未执行提成导入/导出，也没有对业务预期作判断。本文件供“从 GitLab clone，在 SIT 以导入/导出试点框架”的任务实测后修订。用户已明确：普通 SIT 测试应能按任务范围实际导入、回读和导出；不把“完全不写入”设为试点前提。

## 建议的首轮试点最短路径

1. 从 GitLab 的 `lucifer/ai-test-engineer` 做全新 clone，记录提交、版本、安装和 `doctor` 结果；这些只证明本地工具就绪。接到功能名称后先在功能地图及工作项索引查别名，再读历史运行、缺陷和执行资产；已有记录时快速复核本轮 SIT 的入口、角色、版本和数据差异后补测，未找到才做目标功能增量探索。旧版测试结论不能计入本轮通过。
2. 私有试点项目读取当前适用规则/用例、角色和 Fixture；用一张简短运行卡写清“准备用什么测试数据、导入后的预期、如何独立比对和安全停止”。缺正式基线时按快速探针执行并声明临时结论。
3. 在明确的 SIT 测试组织、角色和 Fixture 下准备写前快照/独立 Oracle；经 UI 实际导入一次，保存文件哈希、提交反馈、刷新回读与逐键差异。未知提交结果先核查，不直接重试。随后从 UI 执行导出并与独立预期及范围核对；导出成功和后台 API 响应不能互相代替。
4. 报告分别列产品断言、环境/身份/数据阻塞与框架摩擦；框架问题回流到 `lucifer/ai-test-engineer`，加入合成正反例，再从新 clone 重试同一步。不要把临时试点自动晋升为发布门禁通过。

## 账号与浏览器交接复核场景

截图中的问题拆成“账号身份未在任务开始确定”和“Ego Lite handoff 返回 `UI not available`”两项。历史资料里的账号显示名不证明可用登录凭据；用户已授权 SIT 不等于工具交接已经成功。人工登录时，只有交接工具返回 `done: true` 才能让用户在任务空间操作。账号非唯一时只在任务开始一次询问账号别名与角色/组织，不要临登录才追问。登录后以真实页面或受控身份回读确认环境、角色和组织；不把“账号已选”写成“已经登录”。

回归此问题时逐项核对：唯一账号且已有有效会话应直接使用；多个账号应在登录前一次明确；缺运行时凭据应走安全来源或成功的人工 handoff，不索要聊天密码；用户明确回复继续后，原本用户持有的空间用 `claimTaskSpace`，成功 handoff 的空间用 `takeOverTaskSpace`，不重复索取固定语句；调用返回 `UI not available` 时保留工具错误，不能让用户对不可见任务空间登录，也不能宣称已恢复控制。每种结果只影响相关 UI 步骤，不将工具检查绿灯当产品通过。

## 截图中的回复问题与期望

截图中的助手说“20 项工具检查通过，不能算 SIT 功能通过”是准确的，导出对账工具和导入文件的离线准备也确有进展；但没有交代功能地图、已有工作项与历史运行的命中情况，没把这些准备与本轮将执行的业务探针对上。浏览器任务窗口没有控制权时，笼统请用户回复“继续只读测试”把已指定的 SIT 导入导出变成了只读测试，属于误缩范围。只读诊断是受限步骤的局部手段，不能成为下一轮测试目标。

期望回复按实际证据填四件事，不填虚构历史记录：

> 已在功能地图/工作项/历史运行中查到：〔实际来源和版本，若查无则写查无〕。上次已覆盖〔范围及结论条件〕，本轮待核验〔导入/回读/UI 导出差异〕。当前已完成〔实际业务动作和逐项证据〕；工具检查只证明安装，不是产品通过。SIT 内隔离 Fixture 的常规导入导出在本任务范围内，我将先完成〔下一项可独立执行的步骤〕。目前〔具体 UI 步骤〕因〔已尝试的工具及返回错误〕阻塞；若必须由你恢复窗口控制，说明唯一可执行的恢复动作，恢复后继续原范围，不要求重新授权只读测试。

接受标准：同一需求可以从功能地图和历史运行快速续测；浏览器控制缺失只阻塞对应 UI 动作；框架能列出这次真正执行的业务断言与证据，未测试的明确标“未执行”，不以工具绿灯、准备文件数量或历史通过充作产品结论。当前已调整任务路由说明和 Jev 可选性；真实 SIT 导入、受控运行及正式报告适配仍未实现，需由试点验证和迭代。

试点最低不可省：目标唯一身份、写前状态、独立预期、实际提交反馈和刷新回读、异常状态不盲重试、敏感信息不入仓库。普通 SIT 导入无需把每个点击都变成一份授权文件。上述审查已同步相关任务路由/Skill 文案，合成执行器的代码限制仍未修改；不能将本审查稿当成已实现的 SIT 适配器。
