# 测试上下文索引与加载规则

本索引用于回答“当前测试应先读什么、这些材料各自有什么权威性、怎样证明已经读过”。Skills 只是工作流入口，不是业务知识或正式预期的索引，也不能代替实际读取。

## 功能首测或续测：先恢复已有理解

收到“测试某功能”时，先以功能名称及别名查项目功能地图、`assets/features/`、工作项索引、资产链接和既有执行/缺陷/回归记录，再查适用知识与正式预期。记录命中的路径、版本、环境、上次已覆盖和未完成项；只快速复核当前 SIT 入口、角色、Fixture、版本差异及曾经失败的断言，然后从尚未验证的点继续。历史“通过”只说明当时条件下的结论，不直接继承为本轮通过。地图没有命中时，标记缺口并做目标功能的增量探索；不能仅因没找到索引就要求用户从头讲解，或重新做无关系统全局探索。

若既有 run 曾中断，先核查提交/任务终态及数据现状；未知写入状态不直接重传。能独立推进的知识、Fixture、Oracle、脚本和只读回读继续做，具体 UI 动作在所需执行器无法控制时才单项阻塞。工具静态检查成功不能表述为 SIT 功能通过；也不要因为一个 UI 窗口不可控就请求用户把已授权的 SIT 导入导出测试改为“只读测试”。

## 每个任务的上下文路由顺序

1. **任务状态与决策**：接手已有需求时先读取 `.ai-test/work-items/<ID>/manifest.json`、`workflow-state.json`、`handoff.json`、`decisions.md`、`asset-links.json`、`artifacts.json`、reconciliation receipt，以及当前 run 的 preflight、step receipts 和 closure。以工作项/运行回执为执行状态，不以聊天摘要代替。首次按功能发起任务但没有需求 ID 时，先查功能地图和工作项索引中的别名，再选定已有工作项或创建新项；不要凭“最新一次”选择身份。
2. **仓库入口和测试方法**：读取项目 `AGENTS.md`，以及它指向的 `README.md`、`docs/FRAMEWORK.md` 和适用 Skill。`AGENTS.md` 负责思维宪法与路由，不复制所有细则。
3. **系统知识**：查项目是否有 `knowledge/INDEX.md`、`knowledge/manifest.json`、系统地图、角色/权限模型、实体模型、环境矩阵。存在注册中心时先按其规定 validate，再按功能、阶段、平台、角色 load，并实际阅读全部 `required_reads`。没有注册中心时，搜索并读取仓库内适用的系统知识文件；不能因索引不存在就假定系统没有上下游。
4. **当前业务预期**：读取最新产品决定、已审核需求和业务断言，以及唯一正式测试用例基线。校验稳定 ID、来源、版本和哈希；将正式事实与推断、历史材料、待确认项分开。
5. **测试设计风险**：查遗漏风险规则、权限/列表/数据一致性等方法规范和适用的待决策记录。风险规则提示要测什么，不定义产品预期。待审核候选不得作为正式 Oracle。
6. **执行资产与历史测试**：查功能地图、系统/功能资产注册表、已有用例/页面对象/自动化脚本、共享 helper、包命令、Fixture 工厂、资产复用回执和历史运行；区分旧版通过、已知失败、未完成、阻塞及可复用的导航/Oracle。只复核本轮差异并补缺口，不重复已验证的探索；历史结果不能替代本轮实测。
7. **工具能力与安全边界**：加载目标执行器路由、目标设备能力、环境限制、凭据注入方式、风险动作授权与报告隐私规则。在打开登录页面前，按经审核的账号/Fixture 索引确认 SIT 环境下唯一的非敏感账号别名、角色、组织范围和登录方式；登录后现场核验，历史账号显示名不等于可用凭据。Web 首轮探索核对实际 Ego Lite 或项目执行工具的控制能力；仅在配置 Jev 建议器时检查其可用性。密钥、Cookie、真实个人/顾客数据只从受控运行时来源读取。

## 知识权威性与冲突

优先级：产品经理最新明确决定 → 当前已审核需求/规则/正式基线 → 当前运行的独立证据 → 已验证且适用的资产 → 已审核测试方法/遗漏风险 → AI推断 → 历史聊天与记忆。

发现同一业务口径冲突时，保留冲突双方来源、时间和影响，标记 `conflict_open` 或阻塞；不得用更新时间、检索排名或模型置信度自动裁决。系统观察可以证伪假设，但不能未经确认自动变成需求。

## 项目级知识索引建议

有持续业务知识的项目应提供人类可读 `knowledge/INDEX.md` 和机器可校验 `knowledge/manifest.json`，至少登记：稳定 entry ID、路径、知识类型、适用系统/模块/环境/平台/角色/阶段、权威状态、加载触发条件、来源、复核时间和 SHA-256。建议覆盖：

- 系统生态、导航、角色/权限、实体和跨端关系；
- 已审核业务规则、状态机、已知产品决策和开放冲突；
- 测试遗漏/误判风险规则及测试方法；
- 正式需求/用例基线及其唯一权威来源；
- 执行资产、Fixture 契约、环境差异和恢复方法；
- 待审核学习候选（默认不参与业务预期）。

加载器应返回必须读取的路径、哈希、状态和命中理由。门禁应在执行前验证路径/hash/status 和必读项；Agent 需要回执证明“已读取并理解”，列出本轮适用规则、排除规则和未解决冲突。候选项和过期/未备份资产必须清楚标示，不能混入已审核知识。

如果仓库已有知识注册中心，应复用现有工具，不另造平行注册表。例如私有项目的本地知识注册器可以按 feature/stage 路由规则并校验哈希；框架仓库只提供通用路由、契约和测试工程约束。跨仓库资产只按明确登记的路径引用，权限不足或路径不可读时记为上下文阻塞，不假装加载成功。

## 快速与一站式测试模式的加载范围

快速模式和一站式模式仍执行上述 1、3、4、5、6、7 项的适用部分，特别是第 3 项系统知识和第 5 项遗漏风险规则；不能因为没有正式用例/Current 基线或不逐阶段审核而省略。私有业务仓库先运行知识注册中心 `validate`、按 feature/stage `load`，并实际读取全部 `required_reads`，包括 `knowledge/test-risks/omission-risk-rules.json`。候选风险可以辅助提示，不得作为已审核 Oracle。

每个新测试任务在首个页面/API/设备动作前都必须有已保存的测试计划。标准模式以已审核的任务范围、可用时的正式用例基线、automation-readiness plan 和 pre-execution confirmation 组成计划包；若标准需求探索开始时尚无正式基线，先保存标明基线缺失的只读探索计划，范围/用例审核后再更新并冻结哈希。快速模式以 rapid-test charter 加版本化探针组成临时计划包；一站式模式以带可见 `OP-*` 临时用例、来源哈希和逐步 Oracle 的冻结计划组成。二者都只暂缓正式需求说明书、正式 BF/A 规则审核与正式用例生成，不创建正式测试用例或新基线。一站式模式先向用户展示用例，再连续执行已就绪项，并用同一批ID回填报告；`one-pass-check` 在动作前核计划、收口时核逐步结果。临时章程引用当前知识、正式预期来源（缺失时明确标注）、风险规则、Fixture、断言、独立 Oracle、证据和安全边界。任务没有足够资料时，先执行独立安全的只读探索并标记未知，不能猜定 Oracle。
