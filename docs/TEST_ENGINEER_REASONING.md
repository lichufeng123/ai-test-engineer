# 测试工程师思维协议

本文是所有测试模式共用的思考协议。快速模式可以缩短正式需求、规则和用例产出，但不得删减以下判断。

## 1. 先定义要证明什么

把用户请求转换成测试意图：谁在什么条件下对什么业务对象做什么，系统应发生什么可观察变化，失败会造成什么影响。区分用户目标、实现猜测和真正的业务预期。不要把“点了按钮”“接口返回成功”或“页面有数据”当成业务目标。

## 2. 恢复当前业务模型

执行前先查当前任务状态和适用知识，至少识别：角色与数据范围、关键实体及稳定标识、状态机、上下游消费者、异步环节、持久化/缓存/搜索索引、时间窗口、重试与幂等、清理或恢复方式。根据已有系统地图推导关联链路；未知项标为待确认，不伪装成事实。

## 3. 建立风险假设

按影响与失效可能性排序，主动考虑：主成功路径、权限与越权、边界和无效输入、状态迁移、重复/并发、异常恢复、跨端/下游传播、查询完整性、聚合口径、历史兼容，以及环境、数据、缓存和脚本造成的假阳性。先测能区分风险假设的最小探针，而不是机械遍历页面。

## 4. 每个动作前定义可判定断言

每个可能改变业务状态或影响结论的动作，在执行前写明：

- 目的和前置条件；
- 原子断言及预期状态/值；
- 目标 Fixture 的唯一识别方法、来源、作用域和状态；
- 独立 Oracle：用什么与被测页面/同一接口独立的证据判定；
- 证据点、停止条件、回滚/清理边界；
- 是否只读、是否写入、用户授权范围。

测试目标不能用作主定位条件或 Oracle。不得用两端相同、两个相互依赖视图一致、非空列表或脚本绿灯替代独立业务证据。Fixture 多命中、零命中、身份不一致或 Oracle 不独立时，停止并标为阻塞/待确认，不猜测、不自动选最新记录。

## 5. 动态探索，但不临场漂移预期

探索可以逐步适应新证据：动作前冻结本轮探针的断言、Fixture、Oracle 和停止条件；动作后记录观察、证据及其对模型的影响。新信息只可用于设计下一轮探针；必须说明变更原因并生成新版本/哈希，不能在执行中悄悄改写当前预期。Jev/LLM/浏览器代理只可辅助发现和建议，不得选择业务目标记录或裁决正式结果。

## 6. 执行后定性，不把异常直接报缺陷

逐项对照预期与实际，标记通过、失败、阻塞、未执行。失败需保留可复现步骤、实际/预期和证据。先排除身份、权限、环境、版本、Fixture、异步、缓存、数据范围和自动化问题，再将现象定性为产品缺陷、环境/数据问题、脚本问题、设计如此、证据不足或待决策。未经独立 Oracle 验证的结论不得标通过。

## 7. 判断结论效力与反哺

没有正式审核基线的快速结果标为临时结论，只能支持探索和问题发现，不能冒充完整回归、验收或发布门禁。普通 SIT 测试 Fixture 写入在已指定的功能范围内不自动触发正式规则/用例审核；缺陷、关键链路、发布决策、重复正式回归或暴露业务规则缺口时升级标准流程。一次性探索可附明确责任人与期限的技术债关闭。新知识先进入待审核区，测试方法、业务事实、遗漏风险和执行资产分别归档，不得把观察自动升级为产品规则。

## 输出检查

在测试计划、动作回执和报告中保持以下字段或等价信息：

`测试意图 → 当前模型/知识来源 → 风险假设 → 原子断言 → Fixture → 独立 Oracle → 动作与观察 → 证据 → 结论效力 → 需确认/反哺项`
