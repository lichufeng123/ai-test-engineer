# AI 介入测试识别与路由设计

## 意图

当前框架已经在首轮语义探索、动态答题、陪练对话、证据语义复核和失败诊断中使用 AI，但自动化准备度计划只描述角色、数据、环境、执行目标和硬件前置，没有显式表达“本用例是否需要 AI、AI 做什么、AI 不可做什么”。结果是调用方可能把动态答题、生成内容质量或开放式陪练错误地当成纯 Playwright/Minium 自动化。

本设计建立统一的 AI 测试能力目录和执行前路由门禁。当用户要求执行自动化时，框架必须主动说明建议采用确定性自动化、AI 辅助自动化或混合执行，并在 AI 是必要前置而当前不可用时只阻塞相关用例。

## 已确认目标

1. 识别测试过程中需要 AI 参与的功能，而不是只根据功能名称中是否包含“AI”“智能”判断。
2. 在自动化准备度阶段给出人类可读的执行建议，并生成可校验的机器回执。
3. 明确 AI 的角色、输入输出、可用性、降级方式和结论权限。
4. 保留 Playwright、Minium、API、数据库检查等确定性执行器的职责；AI 不替代页面动作、状态回读和服务端鉴权测试。
5. 在 SIT 99 区建立隔离的回归专用陪练和题库，沉淀审核后的参考答案或回答策略，提高小程序自动化的稳定性。
6. 继续遵守独立 Oracle 原则：生成答案的 AI 或被测产品的 AI 不能单独证明产品评分、标签、摘要或机会识别正确。
7. 把“如何改造业务数据与环境，使动态功能可稳定回归”纳入框架的主动职责；不能只在用户提出具体方案后被动登记。

## 非目标与反目标

- 不因为产品名称带有“AI”“智能”就强制调用模型。
- 不建设第二套正式测试用例基线。
- 不让自由 Agent 取代 Playwright Test、Minium 或其他正式执行器。
- 不把参考答案、页面显示、HTTP 成功、模型自评或两个同源页面一致当作独立 Oracle。
- 不在仓库保存模型密钥、账号、Cookie、真实客户数据、私有接口认证信息或未经脱敏的题目运行记录。
- 不在本设计中直接创建 SIT 99 区业务数据；实际创建前仍需独立测试计划、授权、身份回读、Fixture 唯一性和清理边界。
- 不把某个模块的连锁、门店或权限口径推广到其他模块。涉及权限时仍从当前已审核需求建立逐端权限矩阵。

## 当前状态与依据

当前私有资产已经存在两种 AI 协同模式：

- 自定义陪练由 Minium 负责页面跳转、输入、提交、轮次断言和结果回读，AI 读取当前顾客问题并给出相关回答。运行器通过带 token 的 `answer-request.json` / `answer-response.json` 交接，超时后阻塞，不提交固定无关话术。
- 训练题和随堂小测在题目存在审核参考答案时确定性作答；没有参考答案时触发 `ANSWER_REQUIRED`，等待 AI 根据当前题目和评分要求回答。

框架同时已有 Ego Lite、Jev advisor、Stagehand 和 agent-device 等 AI 探索或辅助能力，但正式 Web 回归仍由 Playwright Test 执行，Jev/LLM 不得改变预期、选择业务目标或裁决正式结果。

缺口位于自动化准备度契约：现有 `automation-readiness` 计划没有 AI 能力、结论权限和降级策略字段，无法确定性地产生建议或阻塞回执。

另一个缺口是缺少自动化可测性建设环节。当前框架容易在既有页面、接口和数据条件下判断“能不能自动化”，却不会系统地反问“能否通过专用组织、专用题库、稳定场景、审核金标或可观测接口，把原本随机的功能建设成可回归对象”。SIT 99 区专用陪练和题库正是这类建设思维的代表，后续必须由框架主动提出，而不是依赖用户补充。

## 考虑过的方案

### 方案一：只增加说明文档

优点是变更最小。缺点是调用方仍可能漏读，无法在 `readiness-plan` / `readiness-check` 中发现缺失能力，也无法证明执行前曾做过判断。因此不采用。

### 方案二：文档、机器目录与准备度门禁统一（已选择）

在公共框架中定义通用 AI 能力契约、Schema、模板、路由规则和测试；在私有业务资产仓库登记当前功能目录。准备度计划按稳定用例 ID 引用能力，生成建议并验证当前是否可用。该方案复用现有 readiness 流程，不引入平行编排系统。

### 方案三：建设独立 AI 自动化编排服务

由服务负责模型调用、动态答案、语义审核和执行器编排。它适合未来的集中式无人值守平台，但现在会引入模型网关、密钥、成本、队列、审计和高可用等额外系统，超出当前需求。因此暂不采用。

## 核心概念

### 执行策略

新版准备度契约中的每条用例都明确一种策略；没有 AI 字段的历史契约继续按兼容规则处理：

- `deterministic`：纯确定性执行。典型为 CRUD、权限、导入导出、状态机、列表/详情回读。
- `ai_assisted`：确定性执行器完成主要动作，AI 负责可替换的建议、生成或复核；AI 不可用时可按已声明降级策略继续部分范围。
- `hybrid_required`：达到该用例目标必须同时使用确定性执行器和 AI；任一侧缺失都阻塞该用例。
- `human_semantic_review`：自动化可以采集证据，但正式语义结论必须由人工或已批准的人工金标作出。

执行策略由已审核用例的测试目标、输入和 Oracle 决定，不能从功能名自动推断。

### AI 能力角色

公共目录支持以下角色：

- `semantic_answering`：根据当前题目或对话上下文生成回答。
- `answer_blueprint_rendering`：依据审核后的回答策略生成本轮具体文本。
- `semantic_quality_review`：对摘要、标签、机会、能力观察、截图或视频内容给出审阅建议。
- `fixture_content_generation`：生成测试录音脚本、文本、语音或其他语义型 Fixture。
- `visual_observation`：读取页面、截图或视频的语义内容。
- `navigation_advisory`：从有限、只读候选动作中建议下一步。
- `diagnosis_and_repair_advisory`：分析失败并提出定位器、等待或恢复候选。

每项能力声明角色、输入契约、输出契约、超时/停止条件、降级策略和 `conclusion_authority`。`necessity` 不属于能力本身，而属于某条用例与该能力的绑定关系；同一能力可以被一条用例设为 required、被另一条用例设为 recommended。

### 结论权限

- `input_provider`：AI 只生成测试输入，不能裁决结果。
- `advisory_only`：AI 只提供建议，必须由确定性断言或人工复核确认。
- `evidence_reviewer`：AI 可标记疑点和候选结论，但正式通过仍需要独立 Oracle。
- `human_required`：该语义结论必须人工确认或使用已批准的人类金标。

不提供“AI 单独正式裁决”权限。

## 公共框架改造

### 文档与模板

新增 `docs/AI_ASSISTED_TESTING_ROUTING.zh-CN.md`，说明识别规则、能力角色、推荐话术、Oracle 边界、隐私与停止条件。README、框架手册和适用 Skill 只引用该文档和强制入口，不复制完整规则。

新增公共 Schema 和示例目录，用于项目登记功能级 AI 测试能力。公共模板只包含虚构示例，不包含伊智内部业务数据。

### 自动化准备度计划

`automation-readiness` 保持向后兼容，新增契约版本。历史版本缺少 AI 字段时继续按原规则处理；新版契约要求每条 `case_requirements` 明确 `execution_strategy`，并使用统一的 `ai_capability_bindings` 数组绑定 `capability_id` 和 `necessity`（required/recommended/optional），避免能力级必要性与三组反向 ID 冲突。

能力项至少包含：

- 稳定 `capability_id`；
- AI 角色；
- 输入与输出契约摘要；
- 结论权限；
- 超时和停止条件；
- 降级策略；
- 受控目录来源与内容哈希。

项目目录是能力定义的受控来源，准备度 source 是本任务的用例绑定和执行目标来源。`readiness-plan` 增加可选 `--ai-capability-catalog` 输入，或从 source 中的 `catalog_ref` 读取同一受控文件；计划回执冻结目录路径/资产 ID 与 SHA-256。目录缺失、哈希不匹配、未知能力或 source 与目录契约不兼容时，新版计划生成失败，不能静默选一方。目录只提供测试方法，不得覆盖已审核需求、用例预期或 Oracle。

目录里的已配置状态仅是历史/配置提示，不代表本次运行事实。执行前确认对每个被引用能力写入 `ai_capability_checks`，包含 `capability_id`、`status`（available/unavailable/unknown）、检查时间和非敏感证据引用；缺少检查等同 unknown。门禁行为为：

1. required 能力缺失且无有效确定性降级：只阻塞依赖用例，返回 `missing_ai_capability_ids`。
2. recommended 能力缺失：保留用例可执行状态并输出警告；它只能增强诊断、证据说明或非门禁洞察，不得承载该 Case 的正式断言或通过条件，也不得改变正式结论范围。若缺失会导致任何正式断言无法裁决，该绑定必须改为 required，或在设计阶段拆成独立 Case。
3. optional 能力缺失：不阻塞，仅记录。
4. AI 可用但结论权限不符合用例要求：阻塞相关用例，不能用“模型已返回”冒充 Oracle。
5. 纯确定性用例不因全局没有模型而阻塞。

准备度回执增加 `execution_recommendations`，以稳定用例 ID 说明建议执行组合、AI 的职责、确定性执行器职责、Oracle，以及 required 能力缺失时可另行执行的已批准子 Case；不得为原 Case 动态缩小结论范围。

### Skill 路由

`ai-test-workflow`、`test-case-generate` 和 `requirement-grounded-functional-testing` 增加统一规则：

1. 在用例设计和自动化准备度阶段判断 AI 是否必要。
2. 用户要求执行自动化时，先读取项目 AI 能力目录并给出建议。
3. AI 必须参与时，明确说出“AI + Playwright/Minium/API”等组合，不能只报执行框架名称。
4. 如果存在审核参考答案、规则表或确定性 Oracle，优先复用；不得为了“智能”而重复调用模型。
5. 模型不可用、低置信、超时或输出不符合契约时安全停止依赖动作，不提交无关固定内容，不悄悄降低断言。

### 自动化可测性建设推导

在给出“适合/不适合自动化”结论前，框架必须先完成一轮可测性建设推导，并把结果写入自动化准备度计划。该推导至少回答：

1. 当前不稳定性来自输入随机、内容生成、时间、外部依赖、角色/组织数据、异步处理，还是不可观察的内部判定？
2. 能否在 SIT 建设隔离且长期保留的专用 Fixture，例如测试组织、测试角色、题库、陪练、录音、顾客、服务或规则配置？
3. 哪些动态输入能够用稳定 ID、版本和内容哈希冻结；哪些必须保留运行时变化？
4. 能否从已审核需求、权威知识或人工评审生成参考答案、rubric、答案 blueprint、负向样本与边界样本？
5. 哪些答案可以转为确定性输入，哪些仍需要运行时 AI；AI 不可用时可执行的最小确定性子范围是什么？
6. 产品输出由什么独立 Oracle 验证；若暂无独立 Oracle，需要建设哪些日志、接口、报告、人工金标或对账数据？
7. Fixture 的创建者、消费者、无权限角色、组织/门店数据范围、写入副作用、保留/清理、漂移检测和维护负责人分别是什么？
8. 这项建设能否复用到更多用例；成本、收益、误报风险和维护债务是否值得？

推导结果分为 `reuse_existing_fixture`、`extend_fixture`、`build_testability_asset`、`runtime_ai_required`、`manual_only_pending_oracle` 或 `not_applicable`，每项都必须记录依据。发现可行的测试资产建设方案时，框架应主动向用户提出具体建议，包括要在哪个环境建设什么、由谁配置、如何冻结、怎样审核、如何路由和如何清理；不能只给出“需要 AI”或“无法自动化”的结论。

这一步只提出并登记建设方案，不自动扩大写权限。真正创建后台题库、陪练、组织或其他业务数据前，仍按测试计划、环境身份、授权、唯一性和清理门禁执行。

新版计划使用 `testability_assessments` 保存机器可读结果。每项按功能登记并绑定稳定 Case ID，至少包含：`assessment_id`、`feature_id`、`case_ids`、不稳定性来源、结论 disposition、依据、拟复用/建设的资产、目标环境、成本与收益、所需前置、负责人/待确认负责人、冻结与漂移检测、清理/保留方式、Oracle 缺口和下一步。所有新增或实质修改的 Case 都必须被一项 assessment 覆盖；历史计划不追溯补录。

当 AI 缺失后只剩一部分断言可执行时，不得把原 Case 继续标为 ready 并在报告中悄悄缩小口径。原 Case 维持 blocked；只有在测试设计阶段已拆分并审核出稳定子 Case、拥有独立 Case ID 和完整预期/Oracle 时，子 Case 才能进入 `ready_case_ids`。首期不引入运行时动态拆分或 assertion 级降级，以兼容现有执行合同。

### Oracle 与人工语义资源契约

新版 Case 为每条正式断言声明 `assertion_oracle_bindings`，每项包含稳定 assertion ID、`required_conclusion_authority`、`oracle_refs` 和用途。用途枚举至少区分 `product_outcome`、`semantic_quality`、`side_effect`、`authorization` 和 `state_persistence`。Oracle 资产可为权威数据源、独立审核的 rubric/语义金标或正式人工复核流程；执行前通过 `oracle_resource_checks` 回读资产 ID、版本/哈希、审核状态、独立性、可用状态和证据引用。缺失、过期、未审核或不独立的 Oracle 只阻塞依赖 Case。

审核参考答案和 answer blueprint 是输入 Fixture，不属于产品结果 Oracle。它们通过 `fixture_resource_checks` 证明“本次提交了哪一个版本、内容和约束”，最多支持输入身份/内容完整性断言；不得绑定 `product_outcome` 或 `semantic_quality`，也不能证明产品评分、标签、摘要或生成质量正确。如果同一权威材料还提供评分预期，必须以独立 Oracle 资产 ID/受控段落登记，并说明为何与被测实现和输入生成过程相互独立。

Case/断言侧的 `required_conclusion_authority` 精确枚举为：

- `deterministic_source`：由独立接口、数据库、事件、设备状态或其他确定性来源证明。
- `approved_semantic_gold`：由独立审核的金标或 rubric 对声明的语义断言进行比对。
- `human_review_receipt`：必须产生正式人工复核回执。
- `composite`：必须同时满足其列出的两个或以上 authority，不允许任选其一。

能力侧的 `conclusion_authority`（`input_provider`、`advisory_only`、`evidence_reviewer`、`human_required`）只是 AI 输出的权限上限和路由约束，永远不能直接满足 Case/断言侧 `required_conclusion_authority`。其中 `human_required` 只是声明后续必须取得人工回执，并不代表 AI 能力本身提供了该回执。

权限兼容规则固定为：

- `input_provider` 只能提供输入，不能满足任何正式结论权限。
- `advisory_only` 和 `evidence_reviewer` 只能提供候选或疑点，不能满足确定性或人工语义裁决。
- 确定性 Case 必须由声明的独立确定性 Oracle 满足。
- 语义质量 Case 只有在审核 rubric/金标命中，或正式人工复核资源可用并产生审核回执时才能裁决；AI 自评不能替代。
- `human_required` 表示最终结论必须具备人工审核回执，不等同于“调用了另一个模型”。

## 私有功能目录

私有业务资产仓库新增 `knowledge/test-methods/ai-assisted-feature-catalog.json`，状态为测试方法知识，不是产品事实或第二套用例基线，并登记到 `knowledge/manifest.json`。

初始目录按当前已登记工作项划分：

| 功能 | 默认策略 | AI 职责 | 确定性职责 |
| --- | --- | --- | --- |
| 自定义陪练三档 | `hybrid_required` | 逐轮语义回答、阻塞分析、证据语义复核 | Minium 页面动作、轮次、评分状态、保存和回读 |
| 训练题/随堂小测 | 条件路由 | 无参考答案时语义回答 | 有参考答案时直接作答；Minium 验证推进、保存、评分报告 |
| 弱项定制陪练 | `hybrid_required` | 按弱项、场景和当前对话生成回答；复核能力观察 | Minium/API 验证身份、链路、状态和持久化 |
| 智能填写服务小记 | `ai_assisted` 或 `human_semantic_review` | 生成内容语义质量复核 | Playwright/API 验证来源、状态、保存、权限和统计 |
| 智能耳机自动标签 | `ai_assisted` 或 `human_semantic_review` | 录音语义与候选标签匹配复核 | 配置、触发、权限、标签写入及顾客详情回读 |
| 智能耳机识别机会 | `hybrid_required` | 判断录音语义是否包含升单、复购、消耗机会 | App/Web/API 验证状态、去向、统计和隔离 |
| 五维记忆、接待分析、能力观察 | `ai_assisted` | 摘要、能力归因和生成内容复核 | 上传、任务状态、实体绑定、聚合及跨端回读 |
| 销冠说 FAQ 归集 | `ai_assisted` 或 `human_semantic_review` | FAQ 聚类、归纳与内容质量复核 | 发帖、互动、权限、媒体及任务状态 |
| 录音语义 Fixture | `ai_assisted` | 生成场景脚本和语音内容候选 | 文件格式、时长、哈希、上传、身份及清理 |
| OCR/截图/视频语义复核 | `ai_assisted` | 视觉/OCR 候选读取和内容审阅 | 文件存在、尺寸、哈希、时间线和独立数据源对账 |

普通导入导出、配置 CRUD、菜单与按钮权限、服务端鉴权、状态迁移和可由独立数据源证明的统计仍默认为 `deterministic`。

## SIT 99 区回归专用陪练与题库

### 目标

在用户指定的 SIT 99 区后台创建只供自动化回归使用的陪练和题库，使题目、场景、评分要求与测试输入具备稳定身份和可追溯版本。用户将该环境称为“SIT 99 区”；实际执行前必须通过环境 profile 和页面/接口身份回读确认环境、区服、组织和账号，不根据历史 `prd/z99` 命名猜测。

### Fixture 隔离

- 使用统一可检索前缀，例如 `QA-AI-REGRESSION-*`，但稳定业务 ID 才是运行时主定位条件。
- 绑定专用测试组织/门店、配置账号和练习员工，不使用真实客户、真实通知或生产题库。
- 登记创建者角色、消费端角色、无权限角色和适用数据范围；后台配置权限与小程序消费权限分别验证。
- Fixture 注册项包含：环境、区服、组织、稳定 ID、名称、用途、题目/场景版本、状态、来源、创建回执、清理/保留策略和最近校验时间。
- 多匹配、零匹配、身份错配、内容哈希变化或权限不明时停止，不按“最新一条”选择。

### 参考答案生成与冻结

题库题目和陪练采用不同策略：

1. **题库题目**：冻结题目稳定 ID、题干哈希、评分要求和审核参考答案。AI 可生成候选参考答案，但候选必须经过人工或权威材料审核后才能标为 `approved_reference`。
2. **开放式陪练**：不把单句固定文案当成万能答案。冻结场景、顾客画像、能力目标、禁区、回答要点和可接受变体，形成 `answer_blueprint`；运行时 AI 根据当前真实问题渲染具体回答。
3. 每个答案或 blueprint 保存版本、来源、审核状态和 SHA-256。运行前同时匹配稳定 ID 与内容哈希；题目变化后旧答案立即失效并回到待审核。
4. 参考答案是测试输入，不是产品评分的唯一 Oracle。正式断言继续核对提交次数、题目身份、评分接口/报告一致性、结束条件、保存与回读；评分语义质量需要独立审核 rubric、人工金标或明确降低结论范围。
5. 用例需要故意低质量答案时，使用审核后的负向 blueprint；如果真实评分意外达标，保存结果并将目标分支标为阻塞，不循环重练直到命中预期。

参考答案与 blueprint 属于私有测试 Fixture，不放入公共框架或测试方法目录。它们保存在 `yizhi-test-assets` 对应销冠小程序 feature/work-item 的受控 fixture 目录，并由资产注册项记录稳定资产 ID、业务对象 ID、版本、内容哈希、来源、审核人/审核回执、状态和适用 Case。准备度之前由专用只读校验检查 `approved_reference`、题目 ID 与题干哈希是否共同命中；任何一项不符都不得走确定性答题。

首期保留现有 `ANSWER_REQUIRED` 请求/响应运行器，不重写统一模型编排器；公共框架只实现目录、路由、前置检查和现有适配器契约校验。待出现第二种不兼容交接协议或需要集中模型治理时，再以独立设计评估统一包装器，避免本轮引入不必要的运行时迁移风险。

### 执行路由

- 题目 ID 和哈希命中 `approved_reference`：Minium 可确定性提交参考答案，不需要运行时 AI。
- 题目无有效参考答案：准备度建议 `AI + Minium`；AI 通过受控请求/响应契约生成答案，Minium 只消费同 token、满足约束的响应。
- 开放式陪练：默认 `AI + Minium`，AI 按 blueprint 和本轮问题作答。
- 仅验证页面、权限、题数、进度或报告结构而不需要真实语义回答：可以执行确定性只读子范围，并在报告中明确未覆盖语义质量。

### 权限和数据范围

实际 Fixture 建设计划必须至少覆盖：

- 后台配置角色能否创建、编辑、启停回归题库/陪练；无权限角色的页面和接口拦截。
- 小程序练习员工只能看到分配给其组织和角色的回归内容。
- 跨组织、跨门店、参数篡改访问必须被服务端拦截且数据不变化。
- 配置变更、撤权和停用何时生效，以及已开始会话、未完成答题和历史报告的处理。
- 后台列表/详情、小程序列表/会话/结果、服务端状态和统计的一致性。

具体允许与禁止口径必须来自销冠小程序当前已审核需求，不能直接套用智能工牌 `REQ-SBA-012` 的业务结论。

## 数据流

```text
已审核用例/临时探针
→ 加载项目 AI 功能目录
→ 生成 automation-readiness source
→ readiness-plan 校验能力引用、结论权限和降级策略并冻结哈希
→ 向用户输出确定性 / AI 辅助 / 混合执行建议
→ pre-execution confirmation 回读当前可用执行器、模型、参考答案和人工审核资源
→ readiness-check 按 Case 拆分 ready / warning / blocked
→ 确定性执行器执行动作，AI 只履行已声明角色
→ 独立 Oracle 与证据裁决结果
→ 报告记录 AI 实际参与范围、模型/答案版本的非敏感指纹、降级和未覆盖项
```

## 异常、停止和降级

- AI 超时、Provider 错误、低置信或输出不符合契约：不提交无关固定答案；阻塞当前语义动作，保留请求指纹和非敏感错误。
- 参考答案不存在、未审核、题目哈希不匹配：不得继续确定性答题；切换到已批准的运行时 AI 路由或阻塞。
- AI 输出包含敏感信息、越权建议或超出题目范围：拒绝消费并记录安全阻塞。
- 被测 AI 返回随机结果：保存真实结果，不通过重复运行筛选想要的答案；需要统计稳定性时使用事先批准的样本量和阈值。
- 语义 Oracle 不独立：只报告结构、状态和一致性结果，语义质量标为阻塞或待人工复核。
- AI 能力缺失只阻塞依赖 Case；权限、配置、题数、页面和其他确定性用例继续执行。

## 测试策略

实现采用测试驱动方式，至少覆盖：

1. 纯确定性计划保持向后兼容，不要求 AI 确认。
2. required AI 能力缺失只阻塞引用它的 Case。
3. recommended AI 能力缺失只产生警告并减少非门禁洞察，不影响 Case 的正式断言和结论范围。
4. 已确认 AI 能力解除对应前置阻塞。
5. 未知、重复或未绑定 Case 的能力 ID 被计划阶段拒绝。
6. `conclusion_authority` 不允许 AI 单独正式裁决。
7. 功能名包含“AI/智能”但用例目标是 CRUD 或权限时，不自动添加模型依赖。
8. 小测有审核参考答案且题目哈希匹配时路由为确定性 Minium。
9. 小测无参考答案时路由为 `AI + Minium`；AI 超时不得提交固定话术。
10. 开放式陪练即使有 blueprint 仍要求运行时语义回答能力。
11. 私有目录通过 Schema 校验且已登记到知识 manifest；候选答案不能冒充已审核答案。
12. README、框架手册、Skill 与示例保持文档同步。
13. 对一个此前未登记的动态问答功能，框架能主动提出“专用 Fixture + 版本化参考答案/blueprint + AI/确定性路由 + 独立 Oracle”的建设建议。
14. 当现有条件不适合自动化但可通过 SIT 数据建设改善时，不允许直接输出永久 `manual_only`；必须登记 `build_testability_asset` 及其成本、前置和负责人待确认项。
15. 能力目录缺失或哈希漂移时新版计划失败；本次能力可用性只能由带证据的 pre-execution check 决定。
16. AI 缺失时原 Case 不得以缩小口径继续 ready；只有预先审核并拥有稳定 ID 的子 Case 可独立执行。
17. 人工语义结论必须校验 rubric/金标或人工复核资源及审核回执，模型自评不能满足该门禁。

## 兼容与迁移

现有 readiness 计划没有 AI 字段时按纯确定性旧行为处理，不批量重写历史回执。首次再次执行已登记的 AI 功能时，根据目录生成新版 readiness plan；历史结果继续保留其当时范围和结论，不追溯升级为 AI 语义质量已覆盖。

已有自定义陪练和训练小测的 `ANSWER_REQUIRED` 文件交接先作为受支持适配器，不立即替换。新契约通过包装层引用其 token、超时和一次性消费语义，避免重建第二套 runner。

## 验收标准

- 用户要求执行已登记功能时，框架能给出确定性、AI 辅助或混合执行建议，并说明各自职责。
- 训练小测能按参考答案状态自动区分纯 Minium 与 `AI + Minium`。
- 自定义/弱项陪练不会被建议为纯 Minium 自动化。
- AI 缺失不会阻塞无关用例，也不会被固定无关话术静默替代。
- AI 生成或复核结果不会成为唯一正式 Oracle。
- SIT 99 区专用陪练/题库方案包含隔离身份、内容/答案哈希、审核状态、权限矩阵、运行路由和清理策略。
- 面对新的动态或生成式功能，框架会先完成自动化可测性建设推导，并主动给出类似专用 Fixture、金标、观测点和降级边界的建设方案，而不是等待用户代为设计。
- 公共框架不包含私有题目、账号、业务 ID、凭据或客户数据。
- 新增及现有专项测试、全量测试、Schema/JSON 校验、文档同步和敏感信息扫描通过。

- 私有目录中当前功能的稳定 entry ID 可按现有知识注册中心命名规范确定。
